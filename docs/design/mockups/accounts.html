Accounts, sign-in and API tokens

Gate 2 replaces the shared admin token with accounts. This page shows every screen and state the UI phase will build, on desktop and on a phone, in light and dark. The variants differ where there is a real choice: where the account area lives, how sign-in handles recovery, and how a new API token is shown. Pick one per choice, or send changes. References, the component check, the final copy and the measurements are in accounts.md.

The screens must

  • Work on both runtimes with no mail server and no outside service.
  • Sign in with a passkey only. No password field, no username.
  • Show a one-time link or a new token exactly once.
  • Name the host command wherever someone can be locked out.
  • Look like the admin that exists: same tokens, Urbanist, header, cards and buttons.

The screens must not

  • Say an account is locked. Failed attempts never block a valid passkey.
  • Let the last owner be removed or demoted, or the last passkey be removed.
  • Let an API token manage accounts or tokens.
  • Add graphics or icons the admin does not already have.
  • Grow the admin script. They ship as their own module.

What other tools do

  • GitHub lists each passkey with a Synced label and asks to confirm a delete. Sessions are revoked one by one.
  • web.dev advises showing created and last-used dates, warning before the last passkey goes, and keeping more than one.
  • Gitea shows a new token once. Tailscale limits key lifetime to 1 to 90 days.
  • Vaultwarden marks pending invitations and offers a resend.

Recommendation

Account area: C. The header keeps the shape it has today, so nothing breaks at 375 px, and the left navigation is the layout the Settings tab already uses. It also has room for what comes next: Step 4 adds project access and Step 6 adds linked identities, each as one more entry.

Sign-in: A. Most visits are a sign-in, not a recovery, so the commands stay one click away. B is the right call if you expect operators to lock themselves out often.

New token: A. A dialog has focus handled by the browser, matches New project and the invitation dialog, and cannot be left half open by navigating away.

Open questions

  • Member access. Until Step 4, a member can use the whole admin except accounts and tokens. The mock says so in the invitation dialog. Is that acceptable for an interim?
  • Token limits. A token limited to some projects cannot create projects or open System. The mock states it in the create dialog. Confirm that rule or ask for another.
  • Recovery and API tokens. Recovery replaces passkeys and sessions and leaves API tokens running, so an agent keeps working while the owner recovers. After a suspected break-in, tokens stay a way in until someone revokes them. Should recovery revoke them too?
