## What the click-through found

- **A token stayed in the page after its dialog closed.** `#tok-out` kept the old value (the form reset does not reach it). The field and the invitation link fields are cleared on close now, and the spec asserts it.
- **The projects page still told a new owner to use `$ADMIN_TOKEN`.** After the first owner it grants nothing. The command uses `$FEEDBACKKIT_TOKEN` (the name `docs/AGENT_SETUP.md` uses).
- **A `429` on the sign-in start showed the server's text** instead of when to try again. It uses the same message as the other `429` paths now.
- **Pasting a new setup link into the tab that shows the setup page did nothing**, because only the fragment changes. The page reloads with the new link.
- **The token dialog started on Write.** It starts on Read now (listed under "differs from the mock" in the design).
- Test-side: two virtual devices holding copies of one passkey drift apart in their sign counters, and the server refuses a counter that goes backwards (it is a cloned authenticator). The spec syncs the newer copy back (`syncPasskeys`), as a synced passkey would behave. This is the server's clone check working, not a defect.

## Not run

- **Firefox and Safari.** Only Chrome ran. The passkey calls use the browser's own JSON helpers (`parseCreationOptionsFromJSON`, `parseRequestOptionsFromJSON`, `toJSON`), which Chrome 129, Firefox 119 and Safari 18.4 ship; the page checks for them and says so where they are missing. That check was exercised in Chrome with `PublicKeyCredential` removed, not in those browsers.
- **A real authenticator** (a phone, a security key, a password manager). The ceremonies ran on the virtual authenticator. The "no passkey found" message depends on how fast a browser answers when it has nothing to offer; that timing was measured on the virtual authenticator only.
- **The Cloudflare runtime in a browser.** The screens were clicked against the standalone server. The Worker serves the same shells and the same API from the same code; the API runs in workerd and on D1 in the conformance suite, and the shells are checked by `test/auth-pages.test.ts`, but nobody opened them against `wrangler dev` or a deployed Worker.
- **A screen reader and keyboard-only use.** Dialogs are native `<dialog>` elements with labels, and Cancel takes the focus in the destructive ones, but no assistive technology was used.
- **A deployed instance over https with a real host name.** Passkeys ran on `http://localhost`.
