# MCP revision 2026-07-28: conformance of `/mcp`, 2026-11-11

What was run: a conformance suite for the parts of [MCP revision 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog) that a read-only tool server meets, on workerd and on Node, and the MCP SDK 2.0.0 client in all three of its version modes against the bundled application. Before it, no test in the repository covered any of this (checked with a search for `server/discover`, `Mcp-Method`, `resultType`, `ttlMs` and `2026-07-28` in `test/`). Based on `main` at `3b00012`.

Result: nothing failed. The Agents SDK 0.27 (`createMcpHandler`) and the MCP SDK 2.0.0 implement the revision, and the gateway's handler passes their behavior through. The suite pins it, so that an SDK upgrade cannot lose it silently, and four limits of the SDKs are pinned and reported.

## Limits of the SDKs, reported

1. `server/discover` and the unsupported-version error list only `2026-07-28`, although clients of 2025-11-25 and earlier are served. `createMcpHandler` builds the SDK handler with `legacy: "reject"` and serves legacy traffic through its own handler beside it, and the SDK's `supportedProtocolVersions` option did not change what discover lists (tried). The spec's examples list both versions for a server that serves both eras. A modern client does not need the other version, so the effect is cosmetic.
2. The tools capability says `listChanged: true`, and `subscriptions/listen` is acknowledged and held open, but a request's tool set never changes, so no notification follows. The SDK adds the flag when tools are registered. Each listener holds a connection for nothing.
3. The `Origin` refusal answers `403` with the code `-32000`. The 2026-07-28 error policy puts `-32000` to `-32019` in the legacy range that new implementations should not use. Only localhost origins are accepted by default, so a page on the gateway's own origin is refused too (the Agents SDK takes `allowedOriginHostnames` to change that; nothing needs it today).
4. An invalid `tools/list` cursor is ignored (one page), where the pagination utility suggests `-32602`.

Not a limit but worth knowing: the 2026-07-28 revision deprecates Dynamic Client Registration in favor of Client ID Metadata Documents. The Worker offers both. The standalone server offers registration only, because the provider's Client ID Metadata Document fetch cannot be kept off private addresses on Node. A client that insists on Client ID Metadata Documents cannot connect to a standalone server (account sessions approve connections there since [the accounts and tokens change](2026-11-11-mcp-accounts-tokens.md), but the Client ID Metadata Document fetch is still off).

## Not covered

- `x-mcp-header` tool parameters, multi round-trip requests (`input_required`), the tasks extension, `io.modelcontextprotocol/logLevel`, OpenTelemetry `_meta` keys, resources and prompts: no tool of this server uses them.
- `ttlMs` is 0 everywhere. A longer hint (the list changes only with a release and a grant) is possible and was left alone: the spec allows 0, and a wrong hint is worse than none.
- Behind the OAuth provider on a real Worker or a public address: the suite calls the handler with the grant's props, and the OAuth layer has its own suites. A real MCP client product was not run.
