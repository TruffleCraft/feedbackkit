# Architecture Decision Records

One paragraph per decision, including the rejected alternative. New resolutions flow here from [`decision` issues](../../issues?q=is%3Aissue+label%3Adecision).

## ADR-001 · 2026-07-13 · Name "feedbackkit" (working title, rename window until announce)

The repo is `TruffleCraft/feedbackkit`. The npm bare name and the GitHub user `feedbackkit` are taken externally (branding collision possible at a public announce); `feedbridge` would be free everywhere. Since v1 needs neither npm nor a domain (self-hosted, script tag), we keep the established working title — renaming is free until the announce and expensive afterward. Final naming: decision issue #9 before the P2 exit.

## ADR-002 · 2026-07-13 · Seed-JSON config in P1, full admin UI in P2 (UC1)

P1 is configured via a Zod-validated seed JSON (identical schema to the later admin config import — not a throwaway artifact); the SCTT migration becomes the P1 exit criterion (consolidation = primary goal first). Rejected: a minimal admin in the MVP (+3–4 PT, ADMIN_TOKEN surface on the critical path, operator population in P1 = 1). The admin experience (Michel's product vision) arrives complete and hardened in P2.

## ADR-003 · 2026-07-13 · P4 providers demand-gated; webhook sink as the universal interim (UC2)

GitLab→Jira→Trello start only once ≥1 external operator asks for a second provider. Until then a normalized JSON webhook sink (P2, ~1 PT) covers any tool via n8n/Zapier/Actions. Rejected: P4 as a fixed calendar commitment (12–17 PT of adapter maintenance before buyer clarity).

## ADR-004 · 2026-07-13 · wrangler.template.toml invariant (fork update path)

The repo commits only `wrangler.template.toml`; the real `wrangler.toml` (operator-specific database_id/bucket) is gitignored and generated by `pnpm deploy` from build variables. Rejected: a real wrangler.toml in the repo (would have broken "sync fork = conflict-free", since upstream touches the file regularly — cron triggers, compatibility_date).

## ADR-005 · 2026-07-13 · Extract-then-form instead of multi-turn chat (carried from the 2026-07-08 review)

ONE LLM call extracts against the per-type required fields; missing items are requested as pre-filled form fields; the second POST is deterministic (server re-validates, re-derives title — no client trust). Rejected: a multi-turn chat loop (turnToken protocol, unbounded LLM cost, biggest UX risk; stays in the backlog if data shows demand).

## ADR-006 · 2026-07-13 · R2 with app-level retention instead of BugDrop's orphan branch

Screenshots/attachments live in R2 (unguessable keys, per-project prefix, `assets` table with expires_at + cron delete + admin-authed delete endpoint). Rejected: BugDrop's orphan branch in the target repo (images in Git history are practically undeletable — GDPR; repo bloat; GitHub-only) and R2 lifecycle rules as the retention mechanism (bucket-level, not per-project controllable). Known residual risk: GitHub's camo proxy caches inline images — documented in SECURITY.md, editing the issue is part of the deletion process.

## ADR-007 · 2026-07-13 · OpenAI-compatible LLM client as an architecture invariant

One client (configurable baseUrl+model+apiKey) covers OpenRouter (default), LiteLLM, Ollama, vLLM and local models. Rejected: provider-specific LLM adapters (unnecessary surface; OpenAI-compatible is the de facto standard).

## ADR-008 · 2026-07-13 · Team-feedback hardening (origin cache, LLM structured output, webhook HMAC)

Three tightenings accepted from team feedback: **(a) Origin check** uses an anchored regex (`^https://…$`, dots escaped, wildcard `*` bounded to `[^./]+`) plus a bounded-TTL isolate cache of the allowlist (≤60 s, keyed on a config-version row) instead of a D1 read per feedback POST — reconciles the earlier "no isolate cache in P1" stance with hot-path throughput (60 s propagation is harmless for origin changes). **(b) LLM extraction** enforces structured output (Zod→JSON schema via response_format/function calling); schema enforcement is best-effort (local models in P5), the hard gate is server-side Zod validation; invalid JSON → immediate seamless fallback with no retry loop. **(c) Webhook sink** signs every POST with HMAC-SHA256 (per-project secret + timestamp against replay) from day 1. Rejected: unsigned webhooks (spoofable), prompt instruction alone without schema enforcement (LLMs hallucinate fields), a D1 read per request (bottleneck under traffic).

## ADR-009 · 2026-07-13 · P0 validation spike skipped

The spike was skipped on Michel's decision. Validating the core thesis shifts to the SCTT migration at the P1 exit (real feedback + the completion-funnel KPI = the same evidence on the real instance). Eval fixtures (10 anonymized SCTT feedbacks) and the p90 < 8 s target moved into the P1 LLM building block; the BugDrop fork check runs as the first P1 task. Deliberately accepted tradeoff: P1 builds on a premise not validated until P1 — both review models flagged the spike as the key de-risking step; the mitigation is watching the funnel closely from the first SCTT day. Rejected: the spike as a hard gate before P1 (Michel: SCTT as his own low-risk property yields the data anyway).

## ADR-010 · 2026-07-13 · Webhook signing scheme locked (HMAC-SHA256, Stripe-style header)

Concrete signing spec for the P2 webhook sink (full reference: docs/WEBHOOKS.md). **HMAC-SHA256** chosen over SHA-384: ecosystem standard (GitHub/Stripe/GitLab/n8n/Zapier verify it out of the box — zero friction), and SHA-384's 64-bit-word CPU edge is nanoseconds, dwarfed ~10,000× by JSON serialization + network latency in a Worker; 256 bits is ample for webhook signatures. Scheme: sign `` `${timestamp}.${rawBody}` `` over the **raw request body** (never a re-serialized object — key ordering/whitespace would break it), header `X-FeedbackKit-Signature: t=<epoch>,v1=<hex>`, 32-byte hex per-project secret in D1, 300 s replay window, receiver uses constant-time compare with a length guard. Two active secrets during rotation. Rejected: SHA-384 (integration friction), signing parsed JSON (non-deterministic), `===` hash compare (timing attack).

## ADR-011 · 2026-07-13 · Default LLM model + cost frame (resolves Q5)

Default `google/gemma-4-26b-a4b-it`, budget 200 calls/day. Recommendations are organized **by category** in [docs/MODELS.md](MODELS.md) (full verified table + method); the seed/QUICKSTART default is the "category 1" pick. Chosen from a live smoke test of FeedbackKit's exact request shape + the OpenRouter models API: extraction is not a reasoning task, so a mid-size model suffices; gemma-4-26b-a4b has vision (screenshots are a core input) **and** structured output, was the cheapest ($0.06/M) *and* fastest (~0.69 s) vision model tested, and — the deciding factor for a privacy-first tool — is **open-weights**, so the SAME model runs hosted (OpenRouter) or on-prem (ADR-007). That collapses the hosted default and the local/privacy default into one pick. **Vision is mandatory** (screenshots are always collected and are a primary input), so text-only models — including OpenAI's cheap/fast open-weights `gpt-oss-20b/120b` — are excluded regardless of price. Categories (all multimodal): fully-managed max-reliability = `gemini-2.5-flash-lite`/`gpt-5-nano`; paid quality step-up for messy input / screenshot OCR = `gemini-2.5-flash`/`gpt-4o-mini`; local/privacy = open-weights `gemma-4-26b-a4b`/`mistral-small-3.2-24b`; free/testing = `gemma-4-26b-a4b-it:free`. All hosted picks are <$0.001/feedback. Rejected "no default, force operator to choose": a sensible cheap default with a documented budget cap serves the ≤15 min TTHW goal better than a blank field. Model stays operator config — this is only the default. `structuredOutput` flag (default true; off for endpoints without strict-schema support, e.g. `gemma-4-31b-it:free`) added to the LLM client so the local-model story (ADR-007) works. NB: an earlier draft wrongly assumed the Gemma tiers were text-only, and first picked gemma-3-27b — corrected to gemma-4-26b-a4b (cheaper + faster) against verified data.

## ADR-012 · 2026-07-14 · Conversational single follow-up (partial reversal of ADR-005)

Live SCTT testing showed the extract-then-form follow-up (three rigid pre-filled required boxes + "noch N Angaben") felt like a form/interrogation — the exact friction the product set out to remove; the old SCTT widget users liked was a single freetext panel. New flow: **freetext first**, and when required info is missing the LLM asks **ONE natural, targeted follow-up question** (composed in POST-1's extraction call via a `followUpQuestion` field), answered in **freetext**; POST-2 does **one** re-extraction of that answer (text-only, budget-gated) and then **always creates** (single-shot — no second question; the answer is folded into the issue so it's never lost). Bounded at **2 LLM calls/feedback max**, both gated by the daily budget. Wire change: `FeedbackResponse` `need_fields` → `follow_up { question, extracted }`; `FeedbackPayload.fields` → `followUpText`. This partially reverses **ADR-005** (which rejected multi-turn chat on unbounded-cost + UX-risk grounds) but explicitly avoids the rejected part: it is a single bounded turn, not an open loop with a turnToken. Widget state `completing` → `asking`. Also reskinned the widget to the SCTT dark-navy/teal "expanding pill" look as the themeable default (light+dark). Rejected: keeping the N-box form (form friction), and full multi-turn chat (unbounded cost — still out per ADR-005).

## ADR-013 · 2026-10-07 · Release channels: every merge is dev, stable after promotion

FeedbackKit serves several embedding apps from one gateway, and the widget is evergreen: a deploy reaches every page on its next load. Without channels a merge would hit every live site at once, with no version to name or roll back to. Modelled on NORA's release channels (NORA ADR-0018), approved by Michel 2026-10-07. **dev:** every merge to `main` builds `vX.Y.Z-dev.N` (version from the tags; the next patch after a stable release by itself, a new minor/major line once via a workflow input), uploads it as a Worker version behind the `dev` preview alias and publishes a GitHub prerelease. **stable:** a `workflow_dispatch` promotes a tested dev tag: the same commit rebuilt as `vX.Y.Z`, deployed to production, released as latest, and the `stable` branch fast-forwarded. Apps choose the channel by gateway URL (production → stable, preview environments → dev alias); both channels share one D1, so migrations must stay expand/contract (ADR-004). Self-hosters follow the `stable` branch with Workers Builds, which settles the update path of Q7 for P2. `/diag` reports version and channel. Rejected: release-please (Actions may not open PRs in the org: `can_approve_pull_request_reviews: false`, and a bump PR per release is noise); a separate dev gateway with its own D1 (double project imports, divergent config); deploying production on every merge (one bad merge reaches every site). Docs: [RELEASES.md](RELEASES.md).

## ADR-014 · 2026-10-08 · Admin UI: Worker-rendered shells plus one vanilla module (resolves Q2)

The admin surface (P2) has three screens: project list, project detail and system. The Worker renders each as a static HTML shell from Hono (`src/worker/admin/pages.ts`, routes `/admin`, `/admin/projects/:id`, `/admin/system`), in the pattern of the landing and test pages. The shells hold no data. A vanilla TypeScript module (`src/admin/main.ts`, built by esbuild to `dist/admin.js`, budget 15 kB gz) reads the token from `sessionStorage`, calls `/api/admin/*` with a Bearer header and writes every API value with `textContent`. Pages carry a per-response nonce CSP (`default-src 'none'`, scripts from `'self'` or the nonce, styles only with the nonce, `connect-src 'self'`, `frame-ancestors 'none'`), `Referrer-Policy: no-referrer` and `Cache-Control: no-store`. `img-src` allows `https:` because each project has its own R2 public base; listing those hosts in the header would show them to anyone who loads the unauthenticated shell. Design tokens and Urbanist come from the marketing site and the gateway's own `/urbanist.woff2`. Rejected: Preact/Vite (a new dependency and a second build for three screens; the theming preview can reuse the widget itself), and a static `dist/admin/index.html` (it would bypass the Worker and take its CSP from `dist/_headers`, which `build:widget` rewrites). **Budget, 2026-11-10:** the admin module budget is 15.25 kB gzipped (was 15 kB). The 0.25 kB pays for the notice about a newer release (journey J2), which the 15 kB left no room for: the module was 15,305 bytes of 15,360. `scripts/check-bundle.mjs` enforces it. **Budget, 2026-11-11:** 15.5 kB. Passkey sessions (Gate 2) need the CSRF header on writes, the account link and the sign-out in the header, and the redirect to `/admin/sign-in` once an owner exists: the module came to 15,651 bytes against 15,616. The account screens themselves are a separate module, `dist/auth.js` (budget 9 kB gzipped), loaded only by their five pages. **Plain layout, 2026-11-11 (variant B of [design/mockups/admin-plain.md](design/mockups/admin-plain.md), picked by the owner):** the admin gets a sidebar (projects with their sections, System, and for owners API tokens and Users), rows instead of cards, a report beside its list from 1180 px, one filled button per screen and red only for failure. The shells keep their shape: static, no data, the same CSP, no inline styles; the sidebar's project list and the sections of the open project arrive from `/api/admin/projects`, and the sections of a project are panels chosen by the address (`#history`, `#history/<report>`, `#setup`, `#types`, `#config`). The admin and the account module share `src/admin/shell.ts` (phone menu, theme switch, project list). **System font:** the admin and the OAuth consent page use the system font; Urbanist stays on the widget, the landing page and the test page, and the admin no longer requests `/urbanist.woff2`. **Controls:** native elements and one stylesheet, no component library. The two reference apps use Ionic Core 9.0.10; measured for this admin (custom elements, esbuild, gzipped JavaScript) it is 35.6 kB for button, input, list, item, label and note, 117.7 kB with segment, toggle, select, textarea and chip, 122.5 kB with modal, alert, popover and toast, against a whole admin module of 15.3 kB. The browser has every control the admin needs. **Budget:** the admin module is 16.75 kB gzipped (was 15.5 kB, 15,662 bytes in use); the layout needs the sidebar and a report view with its actions, and drops the chips, thumbnails, tables and icons. The stylesheet in the shell went from 4.3 kB to about 3 kB gzipped and does not count against the module. Rejected: Ionic Core (size, a CSP review, a rewrite of about 100 kB of source), splitting the project page into a module of its own (a shared core bundled twice and a second script on the one page that needs both).

## ADR-015 · 2026-10-08 · MCP server at /mcp: OAuth 2.1 only, consent through Cloudflare Access

Agents (Claude Code, claude.ai, ChatGPT, Hermes) should read feedback without an operator pasting the admin token into them. The gateway gets an MCP server at `/mcp`, built like NORA's: `@cloudflare/workers-oauth-provider` 1.x wraps the Worker (one provider per origin, resource `${origin}/mcp`, `/oauth/authorize`, `/oauth/token`, `/oauth/register`, Client ID Metadata Documents with `global_fetch_strictly_public`), and the Agents SDK's stateless `createMcpHandler` serves one `McpServer` per request. Identity on `/oauth/authorize` comes only from Cloudflare Access (`verifyAccess`, the admin's Access application gets the path); a grant also needs a click on a consent form with a browser-bound single-use handle. Scopes are read-only: `feedback:read` (projects, feedback, search, funnel) and `config:read` (config export); write scopes come later. The server registers only the tools a grant allows, and the tools reuse the admin API's queries, moved to `src/worker/admin/queries.ts`. Tool descriptions mark feedback as untrusted user content; `hostContext` is returned with `verified: false`. Tool input schemas are plain JSON Schema through the SDK's `fromJsonSchema`, because the SDK wants Zod 4 and the wire contract is on Zod 3. MCP is optional: the KV binding `OAUTH_KV` comes from the build variable `FK_OAUTH_KV_ID`, and without it the OAuth and MCP paths answer 404, so forks deploy unchanged. `/mcp` is rate-limited per grant and hour through the existing D1 counter. Rejected: the admin token as a bearer for `/mcp` (one long-lived secret pasted into every agent, no per-agent revocation, no scopes); a token field on the consent page (it would train people to paste the admin token into pages an app sent them to); a separate MCP Worker (a second deploy, a second set of bindings, and service-binding auth for the same D1 reads). Docs: [QUICKSTART.md](QUICKSTART.md#mcp-for-agents), [SECURITY.md](SECURITY.md#mcp-server-mcp).

**Amendment, 2026-11-11: the plumbing for MCP on the standalone server, off until accounts exist** (the identity part is replaced by the second amendment below; the storage, the shim, the missing Client ID Metadata Documents, the issuer rule and the limits stand). ADR-016 left MCP on the Worker because consent rested on Cloudflare Access. The standalone server now carries the same provider, tools, scopes and limits (`src/worker/mcp/`, `src/worker/oauth/provider.ts`, one code path), but approving a connection needs an identity it does not have: no Access, and accounts arrive with Gate 2 (S11, S12). The owner decided that MCP on the standalone server ships together with accounts, so the identity there is the signed-in account session, and nothing weaker stands in for it. A token typed into the consent form was built and dropped for that reason. **Seam:** `/oauth/authorize` asks one function for who is signing in, `authenticateConsent(request, env)` (`src/worker/oauth/consent-identity.ts`). The Worker leaves `env.CONSENT_AUTHENTICATOR` unset and gets Cloudflare Access, as before. The standalone entry (`src/worker/standalone.ts`) answers "nobody", so consent refuses everyone and the page says that accounts are not built. The account session replaces that function in a small follow-up. **Off by default:** MCP is off on the standalone server, and the start log and `/diag` (`mcp`) say so and why. `FK_MCP=on` serves the OAuth endpoints and `/mcp` anyway, a preview of the plumbing that approves nothing; it needs https, or localhost for a test, and the start refuses an address that would carry a sign-in in clear text. **Storage:** the provider's KV is the table `_fk_kv` in the existing SQLite file (`scripts/server-kv.mjs`), created by the storage shim beside `_fk_objects` and not as a numbered migration (0005 is reserved for Gate 2). It is expand-only, so backup, `feedbackkit-update` and rollback treat it like the rest and an older release ignores it. Expiry is honored on read and swept hourly. One suite (`test/durable/kv-contract.test.ts`) runs the same calls against Cloudflare KV and the adapter. **Runtime shim:** the provider imports the workerd module `cloudflare:workers`; the server bundle aliases it to an empty `WorkerEntrypoint` class (`src/worker/standalone/cloudflare-workers.ts`). **No Client ID Metadata Documents:** the provider would fetch a URL the client chooses, and Node has nothing like the `global_fetch_strictly_public` flag that keeps such a fetch off private addresses, so clients register through `/oauth/register`. Issuer and resource come from `FK_PUBLIC_URL` and never from the request, and registration is rate-limited per client address because it writes to the database that holds the feedback. The tests use a stub identity that exists in test code only; the production build has no way to receive one and a test checks that. Rejected: the `ADMIN_TOKEN` typed into the consent form (built, run and dropped: it puts the one secret that opens everything into a page an app sent the operator to, and the owner wants accounts); an own OAuth server for Node (a second implementation of PKCE, token rotation, hashing and registration for a job the provider already does, and two behaviors to keep equal); keeping MCP Cloudflare-only (the plumbing, the storage and the tests are ready and small). The docs say only that the plumbing exists and is off until Gate 2 ships. The run on a Debian LXC and its limits: [evidence](design/evidence/2026-11-11-standalone-mcp.md).
**Second amendment, 2026-11-11: accounts approve connections, scoped API tokens are a bearer on `/mcp`.** Gate 2 (accounts, passkeys, sessions and scoped API tokens, S11 and S12) is in, so the identity that the first amendment waited for exists. **Consent:** `authenticateConsent(request, env)` now answers with a Cloudflare Access identity or with the session cookie of an account (`authenticateAccount()` of `src/worker/auth/`), on both runtimes, so a Worker that has accounts accepts them beside Access (S15). Any active account may approve, member or owner, because a connection reads what the admin API already shows them. The grant remembers the account (`accountId`, and the provider's user id is the account id), and every `/mcp` call checks that the account is still active, so removing an account ends the connections it approved without touching KV. **Bearer tokens:** a scoped API token (`fk_tok_…`, `src/worker/auth/tokens.ts`) works as `Authorization: Bearer` on `/mcp` through the provider's `resolveExternalToken` hook (`src/worker/mcp/api-token.ts`), so a gateway such as LiteLLM, which connects with `bearer_token` or an OAuth flow it can run, has a way in. The provider has no `client_credentials` grant, and building one would mean an own token endpoint. The token is read-only whatever its access (the tools only read), keeps its project list (every tool filters by it), counts toward the per-grant limit per token, and fails closed: revoked, expired, unknown or an account that was removed is `401` from the next request on, because nothing is cached. Failed tokens are counted per client address with the admin's counter and answered `429` past the limit, and a valid token is never refused for a counter. A token is never read from a URL, never written to a log or an error, and not echoed. This reverses the rejection above of the admin token as a bearer for the case that caused it: that was one long-lived secret pasted into every agent, with no per-agent revocation and no scopes, and a scoped, hashed, revocable token with an end date has none of those. The legacy `ADMIN_TOKEN` is still not a bearer on `/mcp`. **What this is not:** the MCP authorization flow. The specification asks a client to use a token its authorization server issued through OAuth, and the provider's documentation calls an external token a compatibility feature. The token is issued by this gateway, bound to this resource and never forwarded, so it is not the passthrough the specification forbids, but it is a deliberate side door, and the docs say so. **Default:** MCP on the standalone server is on when `FK_PUBLIC_URL` is an https origin (`FK_MCP=off` turns it off, `FK_MCP=on` serves a test on localhost), because nothing can connect before the first owner exists and a connection needs a session or a token. Rejected: a second token type for MCP only (a second thing to create, list and revoke; the account page already lists tokens); a `client_credentials` grant (above); putting API tokens in the OAuth tables (a token created in the admin would then need a copy and a second revocation); and per-token tools or scopes beyond the two read scopes (the tools only read). Open: no admin screen lists OAuth connections, so a connection ends when its account is removed or its grant runs out. [Evidence](design/evidence/2026-11-11-mcp-accounts-tokens.md).

## ADR-016 · 2026-11-10 · Standalone Node runtime beside the Worker (accepted)

Status: accepted by the owner on 2026-11-10 (S16 in [design/scope.md](design/scope.md)). The decision stands now. The standalone runtime counts as supported only when the conditions below are met. Operators should be able to run the whole feedback process on their own Linux host (a home Proxmox LXC, a Hetzner server or any VPS) without a Cloudflare account. Cloudflare stays as the managed option for operators who do not want to host anything. The roadmap kept a Node/SQLite runtime in the backlog behind a Docker checkpoint, which makes this a change of the one-Worker invariant. The proposal: a second entry, `scripts/server.mjs`, runs the same Hono application on Node.js 24 LTS. A small adapter maps the D1 calls the gateway uses (`prepare`, `bind`, `first`, `all`, `run`) and the R2 calls (`put`, `get`, `delete`) onto `node:sqlite`, with attachments stored as blobs in the same database. Migrations run at start. It ships as a release tarball that CI builds from a tag (single-file server, assets, migrations, systemd unit, an update command and a record of release, schema and delivery capability), so an operator needs only Node.js 24 and standard tools (curl, tar, sha256sum, ssh-keygen) and never builds on the server. The checksum file is signed with a release key. Releases follow the channels of ADR-013: stable releases and dev pre-releases, default stable. The contract is one node, one process per database, SQLite in WAL mode on a local disk, and the same behavior tests on both runtimes (a conformance suite), so a difference is a defect or an entry in the parity table of `SELF_HOSTING.md`. OAuth and MCP were Worker-only at first, because ADR-015 built consent on Cloudflare Access; the amendments of ADR-015 on 2026-11-11 put the plumbing on this runtime, and with accounts MCP is on by default there for an https address. Conditions for calling it supported: the review findings R1 to R9 in [design/autonomous-admin-plan.md](design/autonomous-admin-plan.md) are closed, one Node floor is chosen, the tarball and update path (Step D) exist, and a fresh-host verification (Step 3) has run. Rejected for now: Docker as a supported path (the roadmap made it demand-gated and it never ran on this branch), an npm registry package (a publish token and a namespace add supply-chain surface), building on the server (it needs Git and pnpm on every host), a second storage backend such as Postgres (more moving parts for the same single-node promise), and running the Worker through a local emulator in production (not evaluated against the support and upgrade promises operators need, which is an open check before acceptance).

## ADR-017 · 2026-11-11 · Local accounts: passkeys, one-time links and scoped tokens on both runtimes

The only admin credential was the static `ADMIN_TOKEN`, which anyone could lock out with failed attempts and which every agent had to hold. The owner decided in S11, S12, S14 and S15 (2026-11-10) that accounts replace it on both runtimes. The gateway now has two roles, owner and member, and no public sign-up. Sign-in is a passkey through `@simplewebauthn/server` (a maintained library; no hand-written protocol), with discoverable credentials and required user verification. The first owner and recovery use a one-time link that a host command prints (`feedbackkit-admin`, or `pnpm admin:link` with the operator's Cloudflare credentials). The link carries 256 bits in the URL fragment, lives 30 minutes (7 days for an invitation) and works once. Sessions are random tokens stored as SHA-256, in an `HttpOnly`, `SameSite=Lax` cookie (`__Host-` and `Secure` on https), with a CSRF token on every write. Scripts and agents use API tokens that an owner creates: hashed, shown once, read or write, all projects or a list, 1 to 365 days. After the first owner exists `ADMIN_TOKEN` grants nothing and the standalone server starts without it; Cloudflare Access stays an accepted identity on the Worker but is not an account. A valid credential is never refused because of a failed-attempt counter. The exactly-one-owner claim is a primary-key arbiter plus guarded inserts in one `batch()`, which both SQLite and D1 provide; WebAuthn challenges are signed with an instance secret instead of stored. Schema 5 and delivery capability 4 keep an older release from starting on this data. Rejected: passwords (phishable, and reset needs mail, which is not required), a static bootstrap secret (S14), TOTP, OIDC first (Step 6, bound by `iss` and `sub`), stored challenges (a flood of begin requests would need a per-address limit, which is the shared-address problem again), `SameSite=Strict` (the MCP consent page is opened from another site and would show a signed-in person as signed out), signed-token sessions (no revocation), a lockout that also refuses valid credentials (R2), and interactive transactions on D1 (the Worker cannot hold one). Details: [design/gate2-accounts.md](design/gate2-accounts.md), [SECURITY.md](SECURITY.md#accounts-and-sessions).

## ADR-018 · 2026-11-11 · Accounts: one library for the protocol, small hand-written parts for the rest

The owner asked for a comparison before the account screens are built. Method: the official documentation, package pages and, where a page was silent, one source file (blogs and skill pages are no evidence), and a search of the owner's other repositories. **Buy:** `@simplewebauthn/server` 14.1.0 for the WebAuthn protocol (it runs in workerd without `nodejs_compat`, about 88 kB gzipped in the Worker), Hono's `generateCookie` for the session cookie, and the browser's own `PublicKeyCredential` JSON helpers for the screens, with `@simplewebauthn/browser` as the fallback for browsers from before March 2025. **Build:** sessions (a 256-bit token, SHA-256 at rest; Lucia's successor is the same single file and Better Auth stores its session token raw), the CSRF token and origin check (`hono/csrf` does not cover JSON writes), API tokens (the Better Auth API key plugin documents no project list), the failed-attempt counters (Better Auth counts every request per IP, which contradicts "a valid login is never blocked"), and everything the owner's decisions S11, S12 and S14 ask for (the host-command bootstrap, the exactly-one-owner claim, recovery without mail, the last-owner rule), which no library on the list covers. **Replacing the whole stack with Better Auth** (MIT, active, passkey plugin on SimpleWebAuthn) is not worth it now: it owns a second schema and migration system beside the one `feedbackkit-update` and its rollback depend on, it needs D1 migrations through an endpoint, it brings five adapter packages and 2.1 MB, its passkey plugin pins SimpleWebAuthn 13, and the hand-written part that remains would be the same. Revisit at Step 6 (OIDC), with the question whether it can run beside our tables. Rejected: Auth.js (its passkey provider is experimental and lists no D1 adapter), Lucia (deprecated March 2025), a hosted or external identity provider (against S11 to S14). Finding in another repository: NORA hand-writes WebAuthn (295 lines, "zero runtime dependencies" and "no `nodejs_compat`" as reasons); icloud-mcp uses the Python `webauthn` package. The table, the numbers and the sources are in [design/gate2-accounts.md](design/gate2-accounts.md#build-versus-buy).
